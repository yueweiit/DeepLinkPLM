# 基础资料共模映射入口与台账小增量方案

日期：2026-11-10  
状态：讨论稿／待确认，尚未实施。本文仅沉淀方案，不表示正式功能已上线或映射数据已录入。

## 1. 目标与结论

在「基础资料」下、「模具管理」与「手机编码」之间提供「共模映射」入口，建立可查询、可由工程核对维护的手机共模关系台账。

首期采用“独立入口、独立数据写入、只读引用既有模具证据”的小增量方式：不改变原开模审批、编码生成、成品建档、库存及订单链路，不把维护台账等同于实际采用模具。

“优先新增分支”在本方案中的含义是新增独立路由、页面和映射接口；不是在所有老业务入口中加入开关判断。老调用方不传新字段、不切换新接口，原行为保持不变。

## 3. 首期范围与非目标

### 3.1 首期交付

1. 菜单、路由、独立共模映射页面。
2. 列表、分页、关键词、产品／使用机型／基准机型／材质／孔型／状态筛选。
3. 新增、核对维护、停用，保留版本、依据和审计。
4. 只读选择现有产品、手机、工程关系、原模具编码和具体实物套。
5. 展示来源详情；通过已有详情能力查看，缺少安全的现有跳转时首期先展示编号和摘要，不改造旧详情入口。
6. 空数据、无权限、未部署、依赖资料不足分别提示。

### 3.2 首期明确不做

- 不自动从“兼容手机型号”的文字或斜杠分隔名称生成映射。
- 不批量导入、回填、猜测基准机型，不自动新建手机编码。
- 不改变钉钉模板、真实送审、审批结果或审批与新品关联逻辑。
- 不启用新版十位模具编码，不改历史九位刻码。
- 不调用采用确认，不给开模申请注入映射选择，不改变新品第5阶段。
- 不生成模具／成品／SKU／库存记录，不调整BOM、成本或订单制造身份。
- 不把映射有效状态当作新开工、库存或共用生产物料的授权。

首期不增加“草稿／待审／已审”审批状态机。证据不足时不保存为有效映射，并引导工程补齐已有资料。需要草稿收集能力时另行确认增量范围。

## 4. 页面和使用方式

菜单名称「共模映射」，页面标题「手机型号共模映射」。说明文字：本页维护共模关系；保存不等于采用，不改变自身手机及成品编码。

| 列 | 展示内容 |
| --- | --- |
| 产品／款式 | 产品名称，必要时附产品特定码 |
| 使用机型 | 自身手机名称及四位编码 |
| 共模基准机型 | 原模具基准手机及编码 |
| 材质／孔型 | TPU=10、PC=20；大孔／精孔／混合 |
| 结构 | 与工程确认范围一致的结构说明 |
| 原模具编码 | 只读展示，不在此手输或生成 |
| 模具依据 | 主档及具体实物套标识、来源详情 |
| 状态／版本 | 有效、已停用；关系版本 |
| 确认依据／更新时间 | 工程依据及最近维护时间 |
| 操作 | 查看；有工程权限时维护、停用 |

新增顺序：选择产品及使用机型 → 选择孔型、结构、材质 → 选择已有已确认工程关系／实物套 → 确认基准机型 → 填写工程依据和本次原因 → 校验保存。

产品、使用机型、材质、孔型、结构是映射范围，保存后不允许改成另一范围；须停用旧记录再新增。基准、来源依据发生变化时必须重新校验并增加版本。取消、只读查看、筛选不产生写入。

先展示单材质关系，不在首期增加“整套已共模”的推断状态。PC映射有效不代表TPU有效；两个部件分属不同实物套也不能推断整套可用。

没有工程证据时显示缺少哪项资料；接口失败不能显示成“暂无映射”。工程关系失效或版本变化时，应提示需重新核对，不继续标成当前可用。

## 5. 数据与业务约束

关系粒度：产品＋自身手机＋材质＋孔型＋结构 → 原模具身份、基准手机、已确认工程关系及实物套。

核心表优先复用 `plm_mold_share_mapping`：

| 字段组 | 字段 |
| --- | --- |
| 范围 | `product_line_id`、`source_phone_model_id`、`material_code`、`hole_type`、`structure_description` |
| 目标 | `reference_phone_model_id`、`product_mold_code_id` |
| 证据 | `manufacturing_relation_id`、`manufacturing_relation_version`、`evidence` |
| 生命周期 | `status`、`version`、`created_by`、`updated_by`、时间戳 |

校验必须在服务端执行：

- 工程维护权限及产品、主档、实物套对象授权均有效。
- 产品、手机、原模具身份及工程关系存在且处于允许使用的状态。
- 自身手机与基准手机不同；禁止循环和链式转指，直接指向原始基准。
- 同范围最多一条有效映射；并发新增同时有数据库唯一约束兜底。
- 工程关系的产品、使用手机、孔型、结构及版本与本次一致。
- 材质对应的实际原部件编码存在；基准手机与原码手机段一致。
- 编码解析复用 `ProductBusinessCodeGenerator`，历史九位与新版十位均按既有能力识别；不得复制另一套截码或猜码规则。
- 历史码没有孔型位，孔型必须来自工程确认，不能从缺位推断。
- 修改须带期望版本及原因；过期则提示刷新。审计与映射写入同事务，审计失败不得留下无审计写入。
- 停用不删除记录、不依赖已失效的原工程证据、不更改原范围；首期无物理删除接口。

示例仅解释规则：自身1122可按确认依据映射至基准1121的 `MBA10J1121`；1122自身SKU仍使用1122。此示例不是已导入的真实数据，也不构成手机间通用的全局关系。

## 6. 接口方案：保留旧接口，缩小新接口范围

优先沿用本地已经定义的独立命名空间，不改原模具、手机、审批或制造关系接口契约。

| 接口 | 首期用途 | 边界 |
| --- | --- | --- |
| `GET /api/v1/mold-share-mappings` | 分页查询，含`canWrite` | 返回既有响应封装；空表是200空列表，失败不是空列表 |
| `POST /api/v1/mold-share-mappings` | 新增核实映射 | 只写映射与操作日志 |
| `PUT /api/v1/mold-share-mappings/{id}` | 修改依据／目标、停用 | 必须带版本和原因；停用走独立状态处理分支 |

列表筛选沿用 `page`、`size`、`keyword`、`productLineId`、`sourcePhoneModelId`、`referencePhoneModelId`、`materialCode`、`holeType`、`structureDescription`、`status`，复用已有分页约定。前端现有`MappingQuery`缺少`materialCode`类型，需仅在该新模块补齐。

已有本地 `/resolve`、`/confirmations` 及其详情接口不属于首期。如果正式版本已经存在并有调用方，必须原样保留，不删除或改变语义；若正式版本没有，则不随首期新发布。

首期页面移除或不挂接“查看采用记录”入口，因为该入口属于实际采用能力，不是映射维护必需项。前端可保留共享API文件里的未使用声明，但不得因此引入业务调用。

复用 `GET /api/v1/manufacturing-relations` 等现有只读查询及 `ManufacturingIdentityService.requireResolved()` 校验证据；确认其线上版本可用且无写副作用后才能复用。不调用其创建／修改接口来“顺便补齐”工程关系。

## 7. 调用链路与写入边界

### 7.1 查询和维护主链路

```text
基础资料／共模映射
  → Sidebar.vue → router/index.ts → MoldShareMappingView.vue
  → moldSharing.ts → request.ts（原鉴权及响应封装）
  → MoldShareMappingController.page/create/update
  → MoldShareMappingService.page/save
      ├─ PilotAccessService：权限和对象范围
      ├─ 产品／手机／模具身份／工程关系：只读校验
      ├─ ProductBusinessCodeGenerator：原码解析，不生成新码
      └─ 事务写入：plm_mold_share_mapping + 原操作日志
```

### 7.2 选择已有证据

```text
新增／维护弹窗
  → SharedCompatiblePhoneSelector：选择已有手机
  → ManufacturingRelationPicker
  → manufacturing.ts → 既有工程关系查询接口
  → 返回原关系ID、版本、实物套及部件证据
  → 映射保存时后端重新校验，不信任前端带回的原码
```

### 7.3 首期禁止出现的下游调用

映射保存不得继续调用：`resolvePlan`进行采用、`confirm`、开模编码预留、`autoProvision`、新品阶段保存、钉钉送审、库存写入、CRM/MES外发。读取既有证据不等于执行业务采用。

## 9. 数据库兼容与发布路径

实施前先核对，避免与本地并行成果重复建表：

| 正式库状态 | 处理 |
| --- | --- |
| 已有正确映射表及历史迁移 | 直接复用，不重复执行建表；只补确实缺失的新增迁移 |
| 无映射表，2100未执行 | 在正式基线分支新增仅台账迁移；不携带2100整体，也不修改旧视图、旧表约束 |
| 同名表结构或历史不一致 | 停止发布，先比对来源；不自动重建、不覆盖、不Flyway repair |

迁移文件命名建议采用执行时可用的全局唯一版本，示例用途名 `__mold_share_registry_only.sql`；版本号不能在未核对其他任务迁移时提前锁死。

仅台账迁移不创建`plm_mold_share_confirmation`，不改占号视图，不放宽制造关系旧约束。若线上旧约束不支持mixed，首期该孔型显示不可维护并提示需后续升级，不能伪装成other。兼容性限制同时由服务端校验，不只隐藏前端选项。

如果未来再发布完整共模功能，须新增后续兼容迁移，显式处理已存在的台账表和缺失对象；不能直接叠加原2100导致重复建表。该后续合流属于单独发布任务。

发布顺序：确认正式基线 → 基于该基线开发独立分支 → 构建白名单产物 → 生产备份及独立副本迁移／启动验证 → 协调后端部署 → 校验接口及权限 → 部署前端菜单和页面 → 只读验收。前端不得先发布一个会调用不存在接口的入口。

不从当前共享源码直接全量发布，不覆盖线上配置，不重启其他任务占用的本地服务。优先源码分支合并与正常构建，不继续二进制方法级叠补。

回退时隐藏／撤回新入口和台账写入能力，保留映射数据、迁移历史及审计；不删表回退。已产生数据后，只有验证旧程序与新增结构兼容才可退程序，不修改Flyway历史。
